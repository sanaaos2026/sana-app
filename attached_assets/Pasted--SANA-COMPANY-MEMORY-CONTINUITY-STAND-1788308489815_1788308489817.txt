============================================================
SANA COMPANY MEMORY & CONTINUITY STANDARD
معيار سنع لذاكرة الشركة واستمرارية المعرفة
============================================================

PURPOSE:

إنشاء ذاكرة مستمرة لكل شركة داخل سنع بحيث:

- لا يعيد سنع سؤال العميل عن معلومات يعرفها مسبقًا.
- لا تضيع المعلومات بين Case وآخر.
- يمكن للإصدارات القادمة الاستفادة من التاريخ السابق.
- تبقى كل معلومة مرتبطة بمصدرها وفترتها ودرجة صحتها.
- يتعلم سنع كيف تغيرت الشركة بمرور الوقت.
- تستخدم المعلومات السابقة في التشخيص والمهام والقرارات المستقبلية.
- لا تتحول البيانات القديمة تلقائيًا إلى حقيقة حالية.

هذه ليست Feature مستقلة.

هي طبقة مستمرة فوق:
Company
Cases
Evidence
Decisions
Tasks
Impact
Knowledge

2. فصل أنواع الذاكرة
============================================================

قسّم ذاكرة الشركة داخليًا إلى:

A. STABLE PROFILE
معلومات تتغير نادرًا.

مثل:
- اسم الشركة.
- النشاط.
- القطاع.
- نموذج العمل.
- الأسواق.
- المنتجات الأساسية.
- نموذج الإيراد.

B. CURRENT STATE
الوضع الحالي.

مثل:
- الإيراد الحالي.
- الفريق الحالي.
- الأسعار الحالية.
- القنوات الحالية.
- الاختناق الحالي.

C. HISTORICAL STATE
كيف كان الوضع سابقًا.

D. GOALS & TARGETS
ما تريد الشركة الوصول إليه.

E. EVENTS
الأحداث التي غيرت وضع الشركة.

F. DECISION HISTORY
القرارات التي اتخذت.

G. EXECUTION HISTORY
ما تم تنفيذه.

H. OUTCOME HISTORY
ماذا حدث بعد التنفيذ.

I. LEARNINGS
ما تعلمه سنع عن الشركة.

3. لا تستبدل التاريخ
============================================================

مثال:

الإيراد كان:
250,000

ثم أصبح:
180,000

لا تعمل Update على الرقم القديم وتحذفه.

احفظ:

Revenue
Period A = 250k

Revenue
Period B = 180k

ثم أنشئ:

Trend / Change

حتى يعرف سنع:

من أين أتينا؟
أين نحن؟
ما الذي تغير؟

============================================================
4. CURRENT VALUE vs HISTORY
============================================================

لكل معلومة قابلة للتغير:

CURRENT VALUE

+
HISTORY

مثال:

Employees Current = 8

History:
Jan = 5
Apr = 7
Aug = 8

لا تستخدم القيمة التاريخية كحالية بدون تحقق.

5. Information Lifecycle
============================================================

كل معلومة تمر بحالة:

CAPTURED
→ NORMALIZED
→ VERIFIED / UNVERIFIED
→ ACTIVE
→ UPDATED
→ OUTDATED
→ HISTORICAL

لا تحذف OUTDATED إذا كانت مهمة لفهم التاريخ.

لا تستخدمها بصمت.

"آخر تحقق منذ X."

7. Revalidation
============================================================

قبل إعادة استخدام معلومة قديمة:

اسأل:

هل ما زالت صالحة؟

لكن لا تسأل العميل دائمًا.

استخدم:

Source Refresh
أو
Evidence جديدة
أو
Quick Confirmation

مثال:

"آخر مرة كان فريقكم 8 أشخاص، هل ما زال هذا صحيحًا؟"

نعم
تغير
لا أعرف

38. P0 Acceptance Tests
============================================================

TEST 1:
عميل أدخل معلومة في Case سابق؛
لا يسأل سنع عنها مرة أخرى إذا كانت حديثة ومثبتة.

TEST 2:
إذا كانت المعلومة قديمة:
يطلب Quick Revalidation.

TEST 3:
إذا تغيرت القيمة:
لا يحذف القديمة.

TEST 4:
كل قيمة حالية يمكن رؤية تاريخ تغيرها.

TEST 5:
كل Finding يمكن أن يستفيد من Memory ذات الصلة.

TEST 6:
Memory غير المتعلقة بالقضية لا تحمل إلى التشخيص بلا داعٍ.

TEST 7:
معلومة غير مثبتة قديمة لا تتحول إلى Fact بسبب مرور الوقت.

TEST 8:
عند تعارض معلومة جديدة مع الذاكرة:
ينشأ Conflict.

TEST 9:
قرار سابق ونتيجته متاحان عند تشخيص مشكلة مشابهة لاحقًا.

TEST 10:
معلومات العميل لا تتحول إلى General Knowledge تلقائيًا.

TEST 11:
إغلاق Case لا يحذف Evidence أو Learning.

TEST 12:
الإصدار المستقبلي يستطيع إعادة استخدام Company Memory بدون إعادة إدخال البيانات.

39. Definition of Done
============================================================

هذه الحلقة تعتبر مغلقة عندما يستطيع سنع:

معرفة الشركة
↓
حفظ ما عرفه
↓
معرفة مصدره
↓
معرفة متى كان صحيحًا
↓
معرفة هل ما زال صالحًا
↓
استخدامه في القضية الحالية
↓
التعلم من القرار
↓
إعادة استخدام التعلم في القضية القادمة

بدون إعادة بدء التشخيص من الصفر.

"سنع لا يبني تقريرًا عن الشركة كل مرة؛
