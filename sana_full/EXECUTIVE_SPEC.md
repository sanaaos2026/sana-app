# سنع — الوثيقة التنفيذية الموحدة لوكيل تطوير الموقع والنظام

**الإصدار:** 1.0  
**التاريخ:** 16 يوليو 2026  
**الحالة:** مرجع تنفيذ للنسخة التجريبية القابلة للاستخدام  
**مالك المنتج:** فريق سنع  
**إعداد وتجميع:** Manus AI

> **الغرض من الوثيقة:** تحويل الرؤية والمحادثات السابقة وملاحظات فحص النسخة الحية إلى تعليمات واحدة قابلة للتنفيذ. لا تعتبر أي ميزة «منجزة» لمجرد ورودها في محادثة؛ النسخة المنشورة والاختبار الفعلي هما الفيصل.

---

## 1. الأمر التنفيذي للوكيل

ابدأ بجرد النسخة الحالية قبل تعديلها. راجع بنية المشروع وقاعدة البيانات والمسارات والواجهات والاختبارات، ثم قارنها بهذه الوثيقة. لا تعِد بناء التطبيق من الصفر، ولا تحذف وظائف قائمة أو بيانات إنتاج، ولا تفترض أن تنفيذًا تاريخيًا موجود في النسخة الحالية. أنشئ نسخة احتياطية أو فرع عمل، ونفّذ المتطلبات على دفعات صغيرة قابلة للاختبار.

| ترتيب العمل | المطلوب من الوكيل | المخرج الإلزامي |
|---:|---|---|
| 1 | فحص المشروع الحي وتحديد التقنية وقاعدة البيانات والمصادقة | تقرير جرد مختصر يوضح الموجود والمفقود والمتعارض |
| 2 | تشغيل اختبارات المسارات والعزل والصلاحيات | نتائج فعلية قبل التعديل، لا مراجعة كود فقط |
| 3 | إصلاح أعطال الثقة وتجربة الحساب الجديد | نسخة مستقرة بلا روابط مكسورة أو أرقام مضللة |
| 4 | إكمال حلقة القرار والتنفيذ والقياس | قرار له مسؤول وموعد ومقياس نجاح ومهام ونتيجة |
| 5 | بناء لوحة اليوم وSana Score الحي | تجربة تقود المدير بدل عرض بيانات فقط |
| 6 | إضافة نظام مبيعات مبسط | خط فرص ومتابعات ومؤشرات أساسية |
| 7 | ربط الأصول ودفتر القيمة والمراجعة الأسبوعية | قياس واضح لما بُني وتحسن |
| 8 | تنفيذ اختبارات قبول شاملة | تقرير نجاح/فشل مع لقطات أو سجلات اختبار |

بعد كل دفعة، قدّم: الملفات التي تغيرت، الترحيلات المنفذة، الاختبارات، النتيجة، والمخاطر أو القرارات التي تحتاج اعتماد مالك المنتج.

## 2. تعريف المنتج

**سنع** نظام قرار وتنفيذ ونمو موجّه لصاحب الشركة الخدمية. لا يكتفي بتقييم الشركة أو عرض مؤشرات؛ بل يحدد ما يحتاج انتباه المدير، يفسر السبب، يقترح قرارًا، يحوله إلى تنفيذ، ثم يقيس أثره على المبيعات وأصول الشركة. تتفق المصادر السابقة على أن الحلقة الجوهرية هي الانتقال من التشخيص والأدلة إلى القرار والمهمة والأثر، مع خمسة أصول أساسية للشركة.[1] [2]

> **وعد المنتج:** سنع يساعد صاحب الشركة الخدمية على معرفة القرار الأهم، تحويله إلى تنفيذ، وقياس أثره على المبيعات وأصول الشركة.

| السؤال الذي لدى العميل | إجابة سنع المطلوبة |
|---|---|
| ما أهم شيء أعمل عليه الآن؟ | قرار واحد واضح، مدعوم بدليل، مع خطوة تالية |
| لماذا هذا القرار؟ | تفسير مختصر للبيانات والسبب والأصل المتأثر |
| من سينفذه ومتى؟ | مسؤول وموعد ومقياس نجاح إلزامية عند الاعتماد |
| أين تضيع المبيعات؟ | خط فرص بسيط وتنبيه لأي فرصة بلا متابعة |
| هل أصبحت الشركة أقوى؟ | تغير موثق في الأصول ودفتر قيمة قبل/بعد |
| ماذا تعلمنا؟ | مراجعة أسبوعية ونتيجة قرار محفوظة وقابلة للرجوع |

الحلقة التشغيلية المعتمدة هي:

> **قياس الوضع ← اكتشاف فرصة تحسين ← جمع دليل ← اتخاذ قرار ← تعيين مسؤول وموعد ← تنفيذ مهام ← قياس النتيجة ← تحديث الأصل ودفتر القيمة**

## 3. العميل المستهدف

العميل الأول هو صاحب شركة خدمية صغيرة أو متوسطة، يشارك في البيع والتسعير والتسليم وحل المشكلات، ويعاني غالبًا من تشتت المتابعة واعتماد العمل عليه أو على أشخاص محددين. لا يحتاج ERP ضخمًا، بل يحتاج وضوحًا تنفيذيًا أسبوعيًا.

| البعد | تعريف العميل |
|---|---|
| نوع النشاط | شركة خدمات مهنية أو تشغيلية: استشارات، قانون، تسويق، تقنية، تدريب، صيانة، أو خدمات B2B مماثلة |
| مرحلة الشركة | لديها عملاء وفريق وعمليات، لكنها تحتاج نموًا أكثر انتظامًا |
| المستخدم الأساسي | المالك أو المدير العام |
| مستخدمون لاحقون | مدير المبيعات، مدير التشغيل، وقادة الفرق |
| النجاح الأول | الوصول إلى أول قرار معتمد خلال الجلسة الأولى |
| النجاح المتكرر | إكمال مراجعة أسبوعية ومعرفة القرار التالي دون بحث طويل |

## 4. مبادئ المنتج غير القابلة للتفاوض

يجب أن يكون سنع **بسيطًا من الخارج ومنضبطًا من الداخل**. كل شاشة تجيب عن سؤال واضح، وكل توصية تنتهي بإجراء، وكل رقم يملك مصدرًا وفترة تحديث. لا تستخدم اللغة التقنية الداخلية في واجهة العميل إلا عند الحاجة.

| المبدأ | قاعدة التنفيذ |
|---|---|
| القرار قبل المؤشر | لا تعرض لوحة ممتلئة قبل إبراز ما يجب فعله الآن |
| دليل قبل الادعاء | لا يقرر AI أو يفسر درجة دون الإشارة إلى بيانات أو افتراض واضح |
| إجراء تالٍ دائم | كل قرار وفرصة بيع ومهمة لها خطوة تالية وتاريخ |
| توقع لا وعد | أي «ماذا لو» أو أثر مستقبلي موسوم بوضوح بأنه تقدير غير مضمون |
| حالات فارغة موجهة | لا تعرض صفرًا أو قيمة سالبة غير مفسرة؛ اعرض خطوة البدء |
| عزل صارم | لا يرى مستخدم بيانات شركة أخرى تحت أي ظرف |
| أقل خطوة مفيدة | لا تضف نظامًا جديدًا قبل إغلاق الحلقة الأساسية الحالية |
| قياس قبل/بعد | كل تحسين ينتهي بنتيجة موثقة وتعلم محفوظ |

## 5. الهوية والصوت

سنع **منهج وليس شخصًا**. شخصيته المجردة هي «المحقق الاستراتيجي»: يسأل، يستمع، يجمع الدليل، ثم يقترح قرارًا هادئًا وواضحًا. لا تُربط العلامة بوجه أو عمر ثابت، كي يستطيع كل مستشار أو موظف تمثيل المنهج نفسه.[2]

| العنصر | التوجيه المعتمد |
|---|---|
| النبرة | هادئة، واثقة، عملية، خالية من التهويل |
| اللغة | عربية مباشرة ومهنية، بجمل قصيرة ونتائج ملموسة |
| الخط | Cairo ما لم تنص ملفات الهوية الأصلية على غير ذلك |
| الألوان | كحلي، تركواز، ذهبي، رمادي فاتح، رمادي داكن |
| الشعار النصي | «نكتشف الفرص • نصنع النمو» |
| الرمز | إطار بفتحة زاوية مع مربع ذهبي صغير؛ لا يُعاد رسمه دون الأصل |
| الأيقونات | خطية ومتسقة، كحلية مع لمسة ذهبية؛ لا تستخدم الإيموجي كأيقونات أساسية |
| الحركة | انتقالات قصيرة وهادئة تخدم الفهم، لا مؤثرات استعراضية |

لا يخترع الوكيل أكواد الألوان أو ملفات الشعار. إذا لم تكن ملفات SVG والأكواد الدقيقة موجودة في المستودع، يستخدم متغيرات تصميم واضحة قابلة للاستبدال، ويسجل طلبًا لمالك المنتج بدل إنشاء هوية بديلة.

## 6. البنية المعلوماتية والملاحة

أظهرت مراجعة النسخة الحية أن المنتج يملك مكونات واعدة مثل التقييم والتشخيص وجواز الشركة وSOP، لكنها تبدو كأدوات منفصلة، كما ظهرت مصطلحات ومسارات ترفع عبء الفهم.[3] لذلك تعتمد الملاحة على أسئلة العميل لا على أسماء الأنظمة الداخلية.

| القسم الظاهر | السؤال الذي يجيب عنه | المحتوى الأساسي |
|---|---|---|
| **اليوم** | ماذا يحتاج انتباهي الآن؟ | قرار اليوم، المخاطر، الفرص، المتابعات، نبض الشركة |
| **المبيعات** | أين وصلت الصفقات؟ | خط الفرص، المتابعات، مؤشرات التحويل، مصادر العملاء |
| **القرارات** | ماذا قررنا ولماذا؟ | المقترح، المعتمد، قيد التنفيذ، المكتمل، النتيجة |
| **الأصول** | كيف تصبح الشركة أقوى؟ | الأصول الخمسة، مشاريع 90 يومًا، SOP، الأدلة، دفتر القيمة |
| **المراجعة** | ماذا تغير وما خطة الأسبوع؟ | النتائج، التعلم، التعثر، وأولويات الأسبوع التالي |

يستبدل **CEO Home** باسم «لوحة اليوم». وفي واجهة العميل يستبدل مصطلح **القضية** بـ«فرصة تحسين» أو «ملف قرار»، مع جواز إبقاء أسماء الجداول والمسارات البرمجية القديمة داخليًا لتجنب كسر النظام. يدمج «جواز الشركة» داخل الأصول أو التقرير التنفيذي بدل بقائه جزيرة منفصلة.

### مسار Sana الموحد

مسار العميل الأساسي هو: **ملف الأصول `/passport` → Sana Scan → ملخص حي → تقرير تنفيذي**.
يعرض `/passport` الحالة الحالية ودرجة اكتمال الأدلة وسؤال SDS-002 التكيفي الواحد، بينما
يعرض التقرير التنفيذي نتيجة Scan المثبتة ومصادرها وخطة القرار. لا تُعد شاشة Assessment
أو SDS-002 وجهة قرار مستقلة؛ تبقى `/assessment` alias متوافقًا مع الروابط القديمة ويعيد
المستخدم إلى ملف الأصول بعد الحفظ.

| الحالة | المعنى الظاهر للعميل | الإجراء التالي |
|---|---|---|
| `NOT_RUN` | لم تُجمع نتيجة Sana Scan بعد | ابدأ تقييم الأصول ثم شغّل Scan |
| `INCOMPLETE` | بوابة الأدلة مفتوحة ولا يمكن اعتماد نتيجة | أكمل الأدلة المطلوبة وأعد Scan |
| `REVIEW_REQUIRED` | نتيجة قابلة للتتبع بانتظار المراجعة البشرية | راجع التقرير التنفيذي |
| `COMPLETE` | اكتملت مدخلات Scan واعتماد مخرجاته | تابع الأثر من التقرير التنفيذي |

الـaliases البرمجية القديمة (`/company/<company_id>/scan-report`،
`/api/.../scan/report-pdf`، و`/api/.../passport/report-pdf`) تبقى فعالة للتوافق،
لكنها تستخدم نفس مصدر الحالة والنتيجة. يظل التقييم المالي `N/A — Deferred` إلى أن
تُعتمد منهجية وأدلة مالية؛ ويمكن عرض Sana Score كمؤشر تشغيلي مشروط فقط.

## 7. تجربة أول خمس دقائق

لا يدخل المستخدم إلى لوحة صفرية بعد التسجيل. يجب أن يحصل على قيمة أولية قبل أن يُطلب منه إدخال بيانات كثيرة. التسجيل والتهيئة الحاليان بسيطان، لكن أول قيمة بعد الدخول تحتاج توجيهًا أقوى وفق الفحص السابق.[3]

| الزمن المستهدف | خطوة المستخدم | استجابة النظام |
|---:|---|---|
| 0–1 دقيقة | إنشاء الحساب، اسم الشركة، القطاع، حجم الفريق | تخصيص الأمثلة والأسئلة |
| 1–3 دقائق | الإجابة عن 7–10 أسئلة خطوة بخطوة | حفظ تلقائي وتقدم واضح |
| 3–4 دقائق | إدخال ثلاثة أرقام أولية: العملاء/الفرص/الإيراد أو بدائل حسب القطاع | مؤشرات أولية مع تفسير مستوى الثقة |
| 4–5 دقائق | مراجعة أول فرصة تحسين | قرار مقترح جاهز للاعتماد |

بعد الإكمال تظهر الرسالة:

> **اكتشفنا أول فرصة تحسين. راجع السبب، ثم عيّن المسؤول والموعد لنبدأ القياس.**

### معايير القبول

| الرمز | المعيار |
|---|---|
| SOP-01 | لا تفقد المدخلات عند تحديث الصفحة أو العودة لاحقًا |
| SOP-02 | يمكن إنشاء SOP من قرار أو إنشاء قرار من فجوة SOP |
| SOP-03 | النسخة المعتمدة لها رقم إصدار وتاريخ ومالك |
| SOP-04 | AI لا يستبدل اعتماد المسؤول البشري |
| SOP-05 | القوالب تُرشح حسب القطاع ولا تمنع الإنشاء الحر |

## 8. لوحة اليوم

لوحة اليوم ليست Dashboard تقليدية؛ هدفها أن يعرف المدير خلال عشر ثوانٍ ما الذي يتطلب انتباهه والخطوة التالية. فكرة «قرار اليوم» موجودة جزئيًا في الرؤية السابقة، والمطلوب إكمالها بالدليل والأثر والتنفيذ.[1]

| الترتيب | المكوّن | مثال محتوى |
|---:|---|---|
| 1 | تحية وسياق | «صباح الخير. لديك قرار واحد يؤثر في التسليم هذا الأسبوع.» |
| 2 | قرار اليوم | «اعتمد معيار قبول موحدًا لتسليم الخدمة.» |
| 3 | لماذا الآن؟ | «ثلاث حالات إعادة عمل خلال 14 يومًا.» |
| 4 | الدليل والثقة | مصدر البيانات، آخر تحديث، ودرجة ثقة التوصية |
| 5 | الأثر المتوقع | «قد يرفع أصل التشغيل 4 نقاط» — توقع لا ضمان |
| 6 | الإجراء | اعتماد، تعيين مسؤول وموعد، أو طلب معلومات ناقصة |
| 7 | متابعة اليوم | فرصة بيع بلا متابعة، قرار متأخر، مهمة تنتظر دليلًا |
| 8 | نبض مختصر | المبيعات، التنفيذ، الأصول؛ أرقام قليلة ومفسرة |

## 9. Sana Score الحي

الدرجة ليست منتجًا إذا ظهرت كرقم بلا تفسير. الهدف أن تصبح معيارًا حيًا يجيب: لماذا هذه الدرجة؟ ما الذي خفضها أو رفعها؟ ماذا يمكن أن يحدث عند تنفيذ القرارات؟ ورد هذا المحور بوصفه أعلى أولوية لزيادة قيمة المنتج.[1]

### العرض المطلوب

| الطبقة | المحتوى |
|---|---|
| الدرجة الحالية | النتيجة الإجمالية مع تاريخ التحديث ومستوى اكتمال البيانات |
| التفسير | مساهمة الأصول الخمسة وأهم الأدلة التي أثرت في النتيجة |
| التغير | ماذا تغير منذ آخر مراجعة، وما المهمة أو الدليل الذي سببه |
| «ماذا لو؟» | القرارات المعتمدة غير المنفذة وتأثيرها التقديري |
| طريق التحسن | أفضل 1–3 إجراءات حسب الأثر والجهد والثقة |
| المنهجية | رابط يشرح الأوزان والحدود دون كشف أسرار أو خلق دقة زائفة |

> **صياغة إلزامية:** «الدرجة المتوقعة تقدير مبني على البيانات الحالية، وليست نتيجة مضمونة.»

### قواعد الحساب

لا يخترع الوكيل معادلة أو نسبة زيادة في قيمة الشركة. إذا لم توجد منهجية رسمية، يفصل بين **Sana Score التشغيلي** وبين **التقييم المالي**. يمكن تنفيذ بنية قابلة لضبط الأوزان لاحقًا، لكن تظهر الواجهة «المنهجية قيد المعايرة» بدل نسبة مالية مصطنعة.

| الرمز | معيار القبول |
|---|---|
| SCORE-01 | يمكن تتبع كل مساهمة في الدرجة إلى أصل ودليل أو حدث |
| SCORE-02 | توقع «ماذا لو» موسوم بوضوح ومفصول عن الأثر المتحقق |
| SCORE-03 | لا تعرض الدرجة عند نقص الحد الأدنى؛ تعرض نسبة اكتمال وCTA |
| SCORE-04 | أي تعديل في الأوزان موثق بإصدار وتاريخ |
| SCORE-05 | نتيجة الحساب متطابقة في API واللوحة والتقرير |

## 9.1 منهجية القيمة المالية — FIN-001 v1.0

التقييم المالي ليس مكوّنًا تلقائيًا في Sana Scan. إلى أن تُعتمد هذه المنهجية
وتُسجّل أدلتها، تبقى `current_value` و`potential_value` و`value_gap`
`N/A — Deferred` في كل الواجهات والتقارير، حتى لو وُجد `annual_revenue` أو
قيمة صفقة في سجل قديم. لا يجوز تحويل Sana Score أو درجة أصل إلى ريال، ولا
يجوز اعتبار الأثر المتوقع إيرادًا أو تقييمًا للشركة.

### التعريف والمعادلة المعتمدة

هذه المنهجية تقيس **أثرًا ماليًا تشغيليًا قابلًا للمطابقة** لفترة محددة، ولا
تقدّر قيمة الشركة أو قيمة أسهمها:

| الحقل | التعريف عند فتح البوابة |
|---|---|
| `current_value` | هامش المساهمة المتحقق للفترة = الإيراد المعترف به ناقص التكاليف المباشرة المتغيرة، مع العملة والوحدة والفترة |
| `potential_value` | سيناريو مشروط = `current_value` زائد هامش المساهمة الإضافي المنسوب إلى قرار وتجربة موثقة، لا توقع نمو عام ولا ضمان |
| `value_gap` | الفرق بين السيناريو المشروط وخط الأساس، ويُعرض فقط إذا كان كلاهما محسوبًا بالصيغة نفسها |

لا تفتح البوابة إلا عند تحقق **كل** الشروط التالية:

1. تطبيق نسخة FIN-001 المعتمدة، وتسجيل رقم الإصدار وتاريخ الحساب والمسؤول عنه؛
2. مصدر أساسي `Actual` متحقق، ومصدر مستقل ثانٍ للمطابقة، ولكل مصدر مرجع
   وفترة وتاريخ ويد معلومة (عملة/وحدة)؛
3. ثقة كل مصدر لا تقل عن الحد الخاص بنوعه، والمصدر داخل مدة صلاحيته؛
4. مراجعة بشرية تسجل الفترة، وأساس الاعتراف، وأي تسويات أو تعارضات؛
5. لا تُحسب `potential_value` إلا مع خط أساس قبل/بعد، وKPI، وقرار معتمد،
   ودليل يثبت الإسناد؛ وإلا تبقى `N/A — Deferred`.

### المصادر المالية المقبولة

| نوع المصدر | الاستخدام | الحد الأدنى للثقة | مدة الصلاحية من تاريخ الرصد |
|---|---|---:|---:|
| قوائم مالية مدققة | مصدر أساسي لـ `current_value` | 90٪ | 395 يومًا |
| تصدير دفتر محاسبي أو ERP قابل للمراجعة | مصدر أساسي لـ `current_value` | 90٪ | 95 يومًا |
| كشف بنكي أو تقرير مزود دفع | مصدر مستقل للمطابقة | 85٪ | 45 يومًا |
| سجل فواتير قابل للمطابقة | مصدر مستقل للمطابقة | 85٪ | 45 يومًا |
| عقد موقّع | دليل مشروط للالتزام/السيناريو، وليس إيرادًا محققًا وحده | 80٪ | 95 يومًا أو تاريخ انتهاء العقد، أيهما أسبق |
| مقارنة سوقية منشورة | سياق فقط؛ لا تنتج قيمة للشركة ولا تفتح البوابة | 70٪ | 185 يومًا |

المصدر المقبول يجب أن يكون `VERIFIED` ومؤرخًا وله `source_ref` واضحًا. لا
تُقبل الإفادة الذاتية غير المؤرخة، أو لقطة شاشة بلا أصل قابل للمراجعة، أو
تقدير/عرض سعر منفرد، أو benchmark كبديل عن بيانات الشركة. اختلاف العملة أو
الوحدة أو الفترة يوقف الحساب بدل إجراء تحويل صامت.

### الافتراضات وحدود الاستخدام

- العملة والوحدة وفترة القياس حقول صريحة؛ لا تحويل عملة أو سنونة أو استقراء
  غير موثق.
- الأرقام المحاسبية تُعرض كما هي بعد المطابقة، مع فصل `Actual` عن
  `Estimate` و`Forecast` و`Target`.
- الأثر يُنسب إلى القرار فقط عندما يثبت خط أساس قبل/بعد وتوثّق العوامل
  البديلة؛ وإلا يوصف بأنه غير منسوب ولا يدخل دفتر القيمة.
- المخرجات ليست تقييمًا استثماريًا أو ضريبيًا أو قانونيًا، ولا نصيحة مالية،
  ولا وعدًا بالنتيجة. لا تستخدم لاتخاذ قرار تمويلي أو تسعيري دون مراجعة
  المختص المسؤول.
- أي تعديل في المعادلة أو الحدود أو مصدر مقبول يتطلب إصدارًا جديدًا ومراجعة
  أثره على التقارير السابقة؛ لا تُعاد كتابة نتيجة معتمدة بصمت.

**حالة الإصدار الحالية:** `FIN-001 v1.0` معتمدة كسياسة بوابة. لا يوجد حاليًا
سجل مالي لشركة اجتاز المصدرين المستقلين والمراجعة البشرية، لذلك تبقى القيم
النقدية في Sana Scan والتقرير التنفيذي `N/A — Deferred`.

## 10. مسار فرصة التحسين والقرار

تبدأ الرحلة بالملاحظة لا بالحكم، ثم تجمع الأدلة وتختبر الفرضيات قبل اعتماد القرار. هذا من أقوى عناصر المنهج الحالي، ويجب إكماله حتى قياس الأثر.[1] [3]

| المرحلة | مدخل المستخدم | دور سنع | الناتج |
|---|---|---|---|
| الملاحظة | ما الذي يحدث؟ | يطلب رقمًا أو واقعة ويمنع خلط العرض بالسبب | ملاحظة قابلة للقياس |
| الأدلة | ملف، رقم، رابط، أو ملاحظة موثقة | ينظم المصدر والتاريخ والموثوقية | سجل أدلة |
| التشخيص | ما الأسباب المحتملة؟ | يقترح فرضيات وأصولًا متأثرة | 2–3 فرضيات مرتبة |
| الاختيار | ما أفضل قرار؟ | يقارن الأثر والجهد والثقة والاستعجال | قرار موصى به |
| الاعتماد | من المسؤول ومتى؟ | يطلب مسؤولًا وموعدًا ومقياس نجاح | مسؤول، موعد، مقياس نجاح، ومهمة تنفيذية مرتبطة |
| التنفيذ | ما الخطوات؟ | ينشئ مهامًا أو SOP مختصرًا | خطة عمل مرتبطة بالقرار |
| المراجعة | ماذا تغير؟ | يقارن قبل/بعد ويحفظ التعلم | أثر متحقق أو قرار تعديل |

### حالات القرار

| الحالة | المعنى |
|---|---|

| معتمد | تم تحديد المسؤول والموعد ومقياس النجاح |
| قيد التنفيذ | توجد مهام نشطة |
| متعثر | الموعد تجاوز أو يوجد حاجز موثق |
| مكتمل بانتظار القياس | انتهت المهام ولم تكتمل فترة القياس |
| متحقق | ظهر أثر موثق |
| غير متحقق | لم يظهر الأثر، مع سبب وتعلم |
| ملغى | ألغي مع توثيق السبب |

## 12. الأصول الخمسة ودفتر القيمة

الأصول هي: **المعرفة، التشغيل، البراند، البيانات، الاستقلال**.[1] لا تكفي درجة الأصل؛ يجب أن يتحول كل أصل إلى مشروع تحسن يمكن قياسه خلال 90 يومًا.

| الأصل | ترجمته بلغة العميل | مثال مشروع | مؤشر عملي |
|---|---|---|---|
| المعرفة | ما تعرفه الشركة موثق وقابل للنقل | SOP وقاعدة معرفة وتدريب | نسبة العمليات الحرجة الموثقة |
| التشغيل | الخدمة تسلّم بجودة ووقت ثابتين | معيار جودة وقائمة تحقق | التسليم في الموعد وإعادة العمل |
| البراند | العميل يفهم القيمة ويثق بها | عرض قيمة وباقات وحالات نجاح | تحويل الاستفسارات المؤهلة |
| البيانات | القرار يعتمد على أرقام محدثة | لوحة مبيعات وربحية الخدمات | اكتمال البيانات وحداثتها |
| الاستقلال | الشركة لا تعتمد مفرطًا على المالك | تفويض وصلاحيات وبدائل | ساعات تدخل المالك أسبوعيًا |

كل بطاقة أصل تعرض الدرجة الحالية وسببها، هدف 90 يومًا، مشروع التحسين، المسؤول، الدليل، آخر تحديث، والأثر المتوقع. ويجمع **دفتر القيمة** الأثر المتحقق فقط: ما بُني، وما تحسن، والدليل، والتاريخ، والقرار الذي سببه.

## 13. التقييم السريع ومنشئ SOP

التقييم الحالي يغطي عناصر مهمة في المعرفة والتشغيل والبراند والبيانات والاستقلال، كما أن منشئ SOP الحالي يضم عناصر عملية مثل الهدف والمسؤول والخطوات ومعيار القبول والتصعيد.[3] المطلوب ليس حذفهما، بل جعلهما أسهل وأكثر اتصالًا بالقرار والأثر.

| المكوّن | التحسين المطلوب |
|---|---|
| التقييم | سؤال واحد في كل شاشة، حفظ تلقائي، تقدم واضح، وأسئلة تكيفية |
| نتيجة التقييم | فرصة تحسين واحدة أولًا، لا عشر توصيات متساوية |
| SOP | معالج خطوة بخطوة مع قوالب حسب القطاع |
| مساعدة AI | اقتراح مسودة من وصف العملية، مع طلب مراجعة بشرية |
| الاعتماد | مسودة، قيد المراجعة، معتمد، مؤرشف، مع سجل إصدارات |
| الربط | كل SOP مرتبط بأصل أو قرار أو عملية تسليم |

## 14. «اسأل سنع» والذكاء الاصطناعي

المساعد الذكي يأتي بعد اكتمال مسارات البيانات الأساسية. دوره تفسير بيانات الشركة، اقتراح فرضيات وقرارات، وصياغة خطوات أو SOP، لكنه لا يعتمد قرارًا ولا يغير بيانات حساسة دون تأكيد المستخدم.

### عقد الاستجابة

كل إجابة مهمة من AI يجب أن تتضمن قدر الإمكان:

| الحقل | المحتوى |
|---|---|
| الخلاصة | جملة مباشرة تجيب عن السؤال |
| لماذا | البيانات أو الأدلة المستخدمة |
| الافتراضات | ما افترضه النظام لغياب معلومات |
| الثقة | مرتفعة/متوسطة/منخفضة مع سبب |
| الإجراء التالي | خطوة واحدة قابلة للتنفيذ |
| المصدر | روابط داخلية للأرقام أو القرارات أو الأدلة |

### قواعد الأمان والدقة

| الرمز | القاعدة |
|---|---|
| AI-01 | لا تُرسل بيانات شركة إلى سياق شركة أخرى |
| AI-02 | لا يدعي AI نتيجة مالية أو قانونية مضمونة |
| AI-03 | كل اقتراح قرار يحتاج قبولًا بشريًا صريحًا |
| AI-04 | تحفظ المدخلات والمخرجات المهمة مع الشركة والمستخدم والتاريخ وفق سياسة الخصوصية |
| AI-05 | عند فشل المزود تظهر رسالة بديلة ولا تتعطل الرحلة الأساسية |
| AI-06 | فحص Health لا يغني عن اختبار نداء حقيقي في بيئة الإنتاج |
| AI-07 | توضع حدود مهلة وإعادة محاولة وتكلفة، مع تسجيل الأخطاء دون أسرار |

**مؤجل صراحة:** محرك معرفة يشارك أنماطًا بين الشركات. لا ينفذ قبل اعتماد سياسة موافقة وتجميع مجهول ومنع إعادة التعرف. عزل البيانات أهم من أثر الشبكة في هذه المرحلة.[1] [2]

## 15. نموذج البيانات المفاهيمي

لا تُجبر هذه الوثيقة أسماء الجداول الحالية. يحافظ الوكيل على التوافق قدر الإمكان، لكنه يضمن العلاقات التالية. أي ترحيل يجب أن يكون غير هدّام وقابلًا للتراجع.

| الكيان | الغرض | أهم العلاقات |
|---|---|---|
| User | هوية المستخدم وصلاحياته | ينتمي إلى شركة أو أكثر حسب النموذج المعتمد |
| Company | حدود العزل الرئيسية | تملك الأصول والفرص والقرارات والمهام |
| Asset | أحد الأصول الخمسة ودرجته | له أدلة ومشاريع وتأثيرات |
| Evidence | دليل موثق بمصدر وتاريخ وثقة | يرتبط بفرصة تحسين أو أصل أو قرار |
| ImprovementCase | ملف فرصة تحسين | يضم أدلة وفرضيات وقرارات |
| Decision | قرار مقترح أو معتمد | له مسؤول وموعد ومقياس ونتيجة |
| Task | خطوة تنفيذ | ترتبط بقرار وأصل ومسؤول |
| AssetImpact | تغير متوقع أو متحقق | يرتبط بقرار/مهمة/دليل |
| ValueLedgerEntry | سجل قيمة متحققة | يشير إلى الأثر ومصدره وفترته |
| SOP | إجراء تشغيلي بإصدارات | يرتبط بأصل أو قرار أو خدمة |
| Lead/Opportunity | فرصة مبيعات | لها مرحلة وأنشطة وإجراء تالٍ |
| SalesActivity | اتصال أو اجتماع أو عرض | يرتبط بفرصة ومستخدم وتاريخ |
| WeeklyReview | مراجعة دورية | تجمع مؤشرات وقرارات وتعلم |
| AIInteraction | سجل تفاعل مهم | يربط السياق والنتيجة بالشركة مع حماية الأسرار |

### قواعد البيانات

يجب أن تحمل كل السجلات التشغيلية `company_id` أو علاقة عزل مكافئة، وأن تطبق الصلاحية على الخادم لا على الواجهة فقط. يوصى بأن تكون العمليات الحساسة مثل تطبيق حزمة مهام أو تحويل صفقة إلى مشروع **idempotent** لمنع التكرار. وتستخدم معاملات قاعدة البيانات عند إنشاء مجموعة مترابطة من السجلات.

## 16. المصادقة والخصوصية والأمان

ظهرت في المحادثات روايتان تاريخيتان: بيئة Demo تستنسخ شركة C001 لكل Cookie، ونسخة أحدث تعتمد حسابات حقيقية وPostgreSQL. كما أن النسخة التي فُحصت عمليًا تعرض التسجيل والدخول والتهيئة.[1] [2] [3] لذلك يعتمد المنتج **الحساب الحقيقي والعزل في قاعدة البيانات**، ويمكن إنشاء Demo مستقل دون خلطه بإنتاج العملاء.

| المجال | المتطلب |
|---|---|
| المصادقة | تسجيل، دخول، خروج، واستعادة كلمة مرور آمنة |
| الجلسة | Cookies آمنة وHttpOnly وSameSite مناسب وHTTPS |
| التفويض | فحص عضوية المستخدم في الشركة لكل مسار API وصفحة |
| الأسرار | لا تظهر مفاتيح API في الواجهة أو السجلات |
| البيانات | لا تستخدم بيانات العملاء لتدريب أو مقارنة مشتركة بلا موافقة واضحة |
| السجلات | Audit log للأفعال الحساسة مثل اعتماد قرار وتغيير صلاحية وحذف |
| الحذف | سياسة احتفاظ وحذف مع تأكيد وصلاحية |
| النسخ الاحتياطي | نسخة قبل الترحيلات وخطة استرجاع موثقة |
| العرض التجريبي | بيانات مثال غير حساسة، وحسابات أو مساحات منفصلة |

### اختبار عزل إلزامي

أنشئ حسابين وشركتين مستقلتين. أضف في الشركة الأولى دليلًا وقرارًا ومهمة وفرصة بيع، ثم تحقق أن الشركة الثانية لا تستطيع قراءتها أو تعديلها حتى عند استخدام المعرف المباشر في URL أو API. يجب أن يغطي الاختبار كل الكيانات الأساسية، لا الصفحة الرئيسية فقط.

## 17. الحالات الفارغة والأخطاء

المشكلة ليست غياب البيانات؛ المشكلة أن يبدو النظام معطلًا أو يعطي حكمًا دقيقًا قبل أن يعرف الشركة. الفحص السابق لاحظ أرقامًا صفرية وروابط وحالات غير موثوقة.[3]

| الحالة | الرسالة المقترحة | الإجراء |
|---|---|---|
| لا توجد درجة | «نحتاج إجابات إضافية قبل حساب درجة موثوقة.» | أكمل التقييم |
| لا يوجد قرار | «لم نحدد فرصة التحسين الأولى بعد.» | ابدأ التشخيص |
| لا توجد فرص مبيعات | «أضف أول فرصة لنذكّرك بالمتابعة ونحسب التحويل.» | أضف فرصة |
| لا توجد مهام | «اعتمد قرارًا وسيحوّله سنع إلى خطوات.» | راجع القرارات |
| فشل AI | «تعذر التحليل الآن. بياناتك محفوظة ويمكنك المتابعة يدويًا.» | إعادة المحاولة أو فتح نموذج يدوي |
| معرف غير صحيح | صفحة 404 مفهومة دون كشف وجود بيانات شركة أخرى | العودة للقسم المناسب |

تستخدم الأخطاء لغة بشرية، ولا تعرض Stack trace أو أسماء جداول أو ملاحظات تطويرية للعميل.

## 19. اختبارات القبول والدخان

لا يكتفى بفحص أن المسار يعيد 200. يختبر السلوك والبيانات والصلاحية والواجهة. يجب تشغيل الاختبارات على قاعدة PostgreSQL وبيئة قريبة من الإنتاج.

| الحزمة | السيناريو |
|---|---|
| التسجيل | مستخدم جديد ← شركة جديدة ← تهيئة ← أول قرار |
| الدخول | نجاح، كلمة خاطئة، خروج، واستعادة كلمة المرور |
| العزل | حسابان يحاول كل منهما الوصول لمعرفات الآخر عبر UI وAPI |
| القرار | مقترح ← اعتماد ← مهام ← إكمال ← قياس نتيجة |
| الروابط | فتح كل بطاقات القرار والقضية دون Null أو معرف ثابت |
| العدادات | إنشاء/تغيير قرار ثم مطابقة العدد في كل المواضع |
| الدرجة | نقص بيانات، درجة حالية، أثر متوقع، أثر متحقق |
| المبيعات | فرصة جديدة ← انتقال مراحل ← فوز/خسارة ← مؤشرات |
| التحويل | فوز ينشئ بدء تسليم مرة واحدة فقط |
| SOP | إنشاء وحفظ تلقائي وإصدار واعتماد |
| AI | نجاح، مهلة، خطأ مزود، استجابة غير صالحة، وحماية السياق |
| الهاتف | المسارات الرئيسية على عرض جوال دون قص أو أزرار غير قابلة للنقر |
| الوصول | لوحة المفاتيح، التسميات، التباين، وحالات التركيز |

### المطلوب في تقرير الاختبار

| الحقل | المحتوى |
|---|---|
| البيئة | رابط/فرع/إصدار قاعدة البيانات |
| السيناريو | خطوات قابلة للتكرار |
| المتوقع | السلوك الصحيح |
| الفعلي | ما حدث فعلًا |
| النتيجة | ناجح/فاشل |
| الدليل | لقطة شاشة أو سجل مختصر بلا أسرار |
| الإجراء | إصلاح أو قرار مطلوب |

## 21. قرارات مفتوحة لمالك المنتج

لا يحق للوكيل اختراع إجابات لهذه النقاط. يجهز النظام لاستيعابها، ويسجلها كحواجز قرار إن أثرت في التنفيذ.

| القرار | لماذا يلزم؟ | حل مؤقت آمن |
|---|---|---|
| معنى «قيمة الشركة» | يمنع خلط مؤشر تشغيلي بتقييم مالي | استخدم «قيمة تشغيلية» بلا نسبة مالية |
| معادلة Sana Score وأوزانها | أساس الثقة والتفسير | إعدادات قابلة للإصدار ووسم «قيد المعايرة» |
| ملفات الهوية والألوان الدقيقة | يمنع إعادة رسم علامة غير صحيحة | متغيرات قابلة للاستبدال دون اختراع شعار |
| النطاق النهائي وبيئة الإنتاج | يمنع اختبار نسخة غير صحيحة | وثق الرابط والفرع قبل الاختبار |
| رمز دخول Demo | يحدد سهولة الدعوة والحماية | معطل افتراضيًا حتى قرار صريح |
| سياسة الخصوصية واستخدام البيانات | شرط لأي تعلم بين الشركات | لا مشاركة أو تدريب عبر الشركات |
| موقع «هرم سنع» | محتوى منهجي أم مسار منتج | لا يضاف للملاحة قبل قرار |

«هرم سنع» المذكور تاريخيًا يتكون من: **الوجهة، المرآة، الميزان، النسق، الزخم**.[1] لا يضاف آليًا إلى الواجهة قبل تحديد وظيفته ومحتواه المعتمد.

## 22. ما لا يجب بناؤه الآن

| العنصر | سبب التأجيل |
|---|---|
| عشر وحدات BOS كاملة | توسع أفقي قبل إكمال القلب الأساسي |
| Knowledge Graph معقد | لا توجد حاجة مثبتة تبرر التكلفة والتعقيد |
| مشاركة تلقائية للمعرفة بين الشركات | تعارض محتمل مع الخصوصية والعزل |
| تقييم مالي آلي للشركة | يحتاج منهجًا وبيانات واعتمادات مختلفة |
| Dashboard كثيفة | تزيد المعلومات دون زيادة وضوح القرار |
| مؤثرات بصرية وإيموجي كبيرة | تضعف الهوية المهنية ولا تحل مشكلة استخدام |
| إعادة كتابة التطبيق من الصفر | خطر على الوظائف والبيانات دون ضرورة |

خارطة BOS-001 إلى BOS-010 تبقى رؤية مستقبلية؛ BOS-001 لاكتساب العملاء هو الوحيد الموصوف بوصفه معتمدًا تاريخيًا، والبقية مخططة فقط.[2]

## 23. تعريف الإنجاز للنسخة التجريبية

تُعد النسخة جاهزة لإرسالها إلى عملاء محتملين عندما يستطيع كل مستخدم إنشاء حساب مستقل، إكمال تهيئة قصيرة، رؤية أول فرصة تحسين، اعتماد قرار بمسؤول وموعد ومقياس، متابعة مهمة، وتسجيل نتيجة؛ ويستطيع كذلك إضافة فرصة بيع ومتابعتها، دون أن يرى أي بيانات لشركة أخرى.

| بوابة الإطلاق | شرط النجاح |
|---|---|
| الاستقرار | لا روابط Null أو 500 في المسارات الأساسية |
| الخصوصية | نجاح اختبار العزل لحسابين على كل الكيانات |
| القيمة | أول قرار معتمد في أقل من خمس دقائق في سيناريو Demo |
| الدقة | الأرقام والعدادات متطابقة ومفسرة |
| AI | نداء حي ناجح وفشل بديل مُدار |
| الهاتف | الرحلة الأساسية قابلة للاستخدام على الجوال |
| البيانات | نسخة احتياطية وترحيلات موثقة |
| الدعم | وسيلة واضحة للإبلاغ عن مشكلة أو إرسال ملاحظة |
| القياس | أحداث التفعيل والقرار والمراجعة مسجلة دون خلط Demo بالإنتاج |

قبل النشر، يسلّم الوكيل تقريرًا أخيرًا بعنوان **Release Readiness** يتضمن نسخة التطبيق، نتائج الاختبارات، الأعطال المعروفة، القرارات المفتوحة، وخطة التراجع.

## 24. ملخص القرار

القيمة الكبرى لسنع لا تأتي من زيادة عدد الصفحات، بل من ثلاثة أشياء مترابطة: **Sana Score يفسر وضع الشركة، ومحرك قرار يحدد ما يجب فعله، ودفتر قيمة يثبت ما تحقق**. نظام المبيعات المبسط يربط هذا القلب بالإيراد، بينما الأصول الخمسة تربطه بقوة الشركة واستقلالها.

> **قاعدة ختامية للوكيل:** إذا لم تساعد الميزة صاحب الشركة على معرفة القرار، تنفيذه، أو قياس أثره، فهي ليست أولوية للنسخة الحالية.
